사용 가능한 개발 도구로 TypeScript + Three.js + Vite 기반의 고품질 2.5D 픽셀 액션 RPG를 실제 제작하라. 목표는 직접 만든 픽셀 아트·프레임 애니메이션·입체 공간·조명·게임 필을 통합한, 짧지만 완결된 플레이 경험이다. 구현·실행·화면과 모션 검토·결함 수정까지가 이번 요청의 범위다.

## 1. 만들 게임

5~8분에 완주하는 수제 맵을 만든다. 황혼의 계곡 마을 → 물안개 낀 숲과 다리 → 폐허의 신전으로 연결하고, 수호자를 쓰러뜨려 신전의 등불을 되살리면 승리한다. 제목과 세부 디자인은 자율적으로 정하며 사용자용 텍스트는 한국어로 작성한다.

주인공 1명, 안내 NPC 1명, 실루엣과 전투 행동이 다른 일반 적 2종, 공격 패턴이 2개 이상인 보스 1체를 구현한다. 시작·탐색·전투·보스·승리, 사망·재시작이 연결되어야 한다. WASD 이동, 마우스 조준·좌클릭 공격, Space 회피, E 상호작용을 게임 안에서 안내한다.

완주 가능한 게임을 전제로 추가 노력은 아트와 모션 → 공간·조명 통합 → 전투 피드백 → 콘텐츠 양에 투자한다. 인벤토리·제작·스킬트리·절차적 월드·멀티플레이로 범위를 넓히지 않는다.

## 2. 화면의 품질

미술 방향은 ‘따뜻한 등불과 차가운 물안개 속에 살아 있는 작은 입체 디오라마’다. 낡은 석재와 목재, 전경의 가지, 먼 절벽을 조합하고 첫 조작 가능 화면부터 완성된 방향을 보여준다. 마을의 온기에서 폐허의 냉기로 분위기가 이어지고, 승리 후 되살아난 빛이 시각적 보상이 된다. 기존 게임의 고유 캐릭터·맵·에셋은 복제하지 않는다.

픽셀 아트는 제한된 팔레트, 의도적인 픽셀 덩어리와 명암, 식별 가능한 실루엣을 갖는다. 주인공·적·주요 소품을 단순 도형이나 무작위 노이즈로 대신하지 않는다. 화면 전체에 픽셀 필터를 씌우는 것만으로 이 조건을 충족할 수 없다.

지형·건축물·다리에는 실제 높이와 부피가 있어야 한다. 경사로나 계단 오르기, 물 위 다리 건너기, 나무·기둥 앞뒤 통과가 가능하고 충돌·발 위치·가림이 보이는 공간과 일치해야 한다. 전경·중경·후경을 구분하며 캐릭터의 밝기·색감·접지 그림자를 주변 조명과 통합한다.

움직이는 물, 바람에 반응하는 식생, 절제된 분위기 입자를 구현한다. 사선 직교 또는 완만한 원근 카메라 중 적합한 것을 선택하고 안정적인 추적과 짧은 연출을 지원한다. Bloom·DOF·반사·커스텀 셰이더는 필요에 따라 선택한다. 후처리를 꺼도 구도와 기본 아트가 성립하고, 켰을 때 픽셀과 전투 판독성이 유지되어야 한다.

## 3. 모션과 조작감

주인공은 최소 4방향과 대기·이동·공격·회피·피격·사망 동작을 갖는다. 좌우 미러링은 허용하지만 앞뒤는 구분한다. 포즈와 실루엣이 바뀌는 실제 프레임 애니메이션을 만들며, 한 장의 스프라이트에 이동·회전·확대만 적용해 모든 동작을 대신하지 않는다. 적과 보스도 공격 예고·타격·피격·사망을 읽을 수 있어야 한다.

원본 픽셀 해상도와 프레임 수는 화면상 크기와 동작에 맞게 정한다. 프레임마다 캐릭터 크기·발 기준점을 유지하고, 동일 크기 캔버스에 무기·망토가 잘리지 않는 여백을 확보한다. 원본 픽셀 밀도는 일관되게 유지하되 원근에 따른 화면상 크기 변화는 허용한다.

공격은 준비 → 타격 → 회수의 리듬을 갖는다. 명중 순간에 짧은 hit-stop, 방향성 스파크, 적의 반동, 절제된 카메라 충격과 효과음을 맞춘다. 강한 공격은 예고와 충격의 크기로 구분한다. 회피는 즉각적으로 반응하고, 공격 판정·회피 가능 시점은 보이는 동작과 일치해야 한다. 소리를 꺼도 명중·피격·위험을 알아볼 수 있어야 한다.

스프라이트의 확대·축소 필터링을 구분해 결정하고, 실제 이동 중 픽셀 떨림·잔상·프레임 튐·발 미끄러짐·가림 오류를 수정한다. 정지 화면의 선명함만으로 모션 품질을 판단하지 않는다.

시작에는 스킵 가능한 짧은 타이틀·카메라 연출을, 보스 진입에는 환경 변화·등장 동작·이름 표시를, 승리에는 등불과 환경의 변화를 결합한다. HUD는 체력·목표·필요할 때의 보스 체력을 중심으로 작게 구성하고 메뉴까지 같은 미술 방향을 유지한다. 공격·피격·회피·보스·UI 효과음과 환경음을 제공한다. Web Audio 합성은 허용하며 시작 입력 후 오디오를 활성화하고 음소거를 지원한다.

## 4. 제작 조건

Three.js를 핵심 렌더러로 사용한다. 시각 에셋은 직접 작성한 코드·픽셀 데이터·셰이더로 제작하고 재생성 코드와 필요한 시드를 남긴다. 외부 이미지·영상 생성 모델과 완성형 에셋팩, 기존 게임 구현은 사용하지 않는다. 개발 라이브러리·공식 문서·오픈 라이선스 한글 폰트는 허용한다. GLB 내보내기나 별도의 모델링 파이프라인은 요구하지 않는다.

게임 상태·렌더링·UI의 책임은 나누되 범용 엔진을 별도로 만들지 않는다. Windows 11의 Node.js 환경에서 설치·개발 실행·타입 검사·프로덕션 빌드가 가능하도록 npm 명령과 lockfile을 제공한다. 백엔드·인증·유료 서비스·배포는 범위 밖이다.

## 5. 자율 실행 범위

작업 폴더의 적용 지침과 기존 변경을 존중한다. 이 프로젝트에 필요한 파일 생성·편집, 로컬 의존성 설치, 에셋 생성, 개발 서버 실행, 브라우저 테스트와 결함 수정은 수행 범위에 포함된다. 디자인과 구현의 가역적인 선택은 직접 결정하고, 계획이나 첫 구현을 보고한 뒤 재승인을 기다리며 멈추지 않는다. 기존 사용자 작업 삭제나 작업 폴더 밖의 설정 변경으로 문제를 해결하지 않는다.

대표 장면에서 최종 방향의 아트·이동·전투를 함께 맞춘 뒤 전체 동선으로 확장한다. 세부 구현 순서는 직접 정한다. 필요한 문서와 코드만 읽고, 진행 기록은 완료·미완료·실제 장애물을 식별할 정도로 유지한다.

검증 도구는 작게 만든다. 개발 모드에서 대표 장면으로 진입하고 현재 게임 상태와 필요한 렌더링 통계를 읽을 수 있으면 충분하다. 관측한 결함과 요구사항을 기준으로 수정하며, 변경·실패·미해결 문제가 없으면 통과한 검사를 반복하거나 검증 범위를 확대하지 않는다.

## 6. 완료 판정과 제출

최종 빌드에 대해 다음 증거를 남긴다.

- 실행: 타입 검사·프로덕션 빌드 통과. 정상 조작으로 시작부터 승리·재시작까지 완주하고 사망·재시작도 확인한다. 개발용 장면 진입이나 강제 승리를 완주 증거로 쓰지 않는다. 진행 차단 오류·누락 에셋·처리되지 않은 런타임 오류를 해결한다.
- 시각과 모션: 마을·숲 전투·보스전의 실제 스크린샷, 주인공 스프라이트 시트의 원본·정수배 확대, 이동·방향 전환·공격·회피·전경 뒤 통과의 영상 또는 연속 프레임을 저장하고 직접 확인한다. 판독성·접지·가림·픽셀 선명도·움직임·UI 간섭을 점검한다. 캡처 파일의 존재만으로 통과 처리하지 않는다.
- 성능: 데스크톱 Chrome, 1920×1080, DPR 1에서 60 FPS를 목표로 한다. 워밍업 후 30초 전투 구간의 평균 FPS·p95 프레임 시간과 실제 측정 환경·렌더링 해상도를 기록한다. 하드웨어 가속과 소프트웨어 렌더링을 구분한다.

소스·에셋 생성 코드·검증 증거와 함께 README에 실행 명령·조작법·검증 결과·남은 결함을 정리한다. 기능 통과와 시각적 품질은 별도로 판단한다. 도구 제약으로 확인하지 못한 항목은 미검증으로 남기고 가능한 나머지 작업을 마친다. 조건을 충족하면 제출하며, 충족하지 못한 부분은 구체적으로 보고한다. 최종 응답에는 결과물 위치·실행 방법·검증 결과·남은 문제만 제시한다.
